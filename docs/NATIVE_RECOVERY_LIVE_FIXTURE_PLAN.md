# Full RepoRebuild live campaign — phase A / C0

This opt-in planner is separate from canonical CLI and ordinary live CI. It does not modify the minimal disposable test or the recovery engine. No live case has passed. It builds a private local plan and synthetic Git seed. The separately approved create-primary action only creates an empty private standalone primary and disables Actions; it never pushes source, deletes, merges, dispatches, grants credentials or repairs secrets. The POST intent is exclusive and durable; if any outcome is uncertain, stop and review the exact ID and receipts, never replay. The creation stage is not the recovery acceptance gate.

Role suffixes p/m/n/h/c/d/f/k distinguish primary rich, minimal, negative, host, second consumer, dependency, fork parent and fork child. Primary doubles as first consumer. All are proposals, not authorization. Fork and org support need separate feasibility review; a same-owner private fork may be impossible. No production parent, MMRL profile substitution or shared repository credentials. The minimal fixture uses the existing unmodified narrow harness.

Phase A / C0 provides source pin, exact owner and slug plan, private storage, independent filesystem check, same actor admin token probe, local Git refs, annotated/lightweight tags, deterministic synthetic release assets, LFS object if installed, inert PR and dispatch workflow sources with pinned upload-artifact action, branch-only file and failure/canary path. --smoke-without-lfs cannot bootstrap a full fixture. GitHub branch protection, issues/PRs, release archive, environment policies, secrets/vault, App/PAT, cross-repo and actual live workflow are not yet provisioned. Fresh native source qualification is required after delivery and before approving fixture creation.

Phase C1 will independently compare exact seed refs and blob hashes, push to the observed empty fixture only after exact identity/scope approval, populate metadata under per-write durable intent and then enable the approved audited workload. Phase D must check native prepare/verify plus independent copies, validate exact inventories and drift refusal, and request separate deletion approval. Phase E/F must use actual native execute/resume and independent comparisons. Phase G needs actual fixture-only credentials and workloads. Phase H uses per-row verified evidence; no acceptance from self-authored ledger or summaries alone.

The following original handoff plan and feature matrix are preserved for review. All live statuses are NOT_RUN.

# Comprehensive live acceptance campaign — proposed, NOT EXECUTED

## Objective
Test native repository recovery end-to-end on synthetic GitHub data, including every supported feature and each historical MMRL failure path. One primary rich disposable repository is the goal; a minimal baseline fixture and auxiliary repositories are justified for incompatible topologies or isolated cross-repository behavior. Never describe a live mock, no-op, skipped feature, or old successful CI as current operational evidence. The test matrix is a review baseline; enumerate any additional implemented behaviors from the exact snapshot and full checkout before freezing it.

## Gate A — plan and bind source, operator and fixture identities
1. Read `evidence/accepted-state.json`; query live PR and main, require exact source or separately review drift. Inspect canonical CLI schema and source; confirm local clean named feature checkout. Re-run focused recovery regressions if appropriate. Inspect existing native session; no duplicate actions dispatch. No remote fixture creation until the plan and scope are explicitly authorized.
2. Inventory tools/availability: Bash, distribution Python, Devtool runtime, git, gh, git-lfs, age, jq, sha256sum; API permissions and available GitHub features. Use private Termux HOME; inspect free space and actual `st_dev` and ownership of an independently backed up separate filesystem (not merely a second directory, Android shared storage, or unsafe mount). If independent filesystem unavailable, report blocked; do not use local-only waiver. Verify `gh` lifecycle actor, explicit separate `DEVTOOL_RECOVERY_ADMIN_TOKEN`, both current exact-repository admin permissions, same actor, HTTPS origin, and creation/deletion capability prerequisites. Permission observations are not future authorization proof; don't expose credentials or grant unrestricted production access. Use a secure local source; never print `env`, gh token, Authorization headers, vault contents or secrets. PAT and App credentials must be limited to the disposable campaign; separate management authority only where genuinely necessary. Do not pass secrets on command lines.
3. Generate a high-entropy campaign ID. Every remote resource must belong to an explicit exact-name allowlist, record numeric repository IDs, account, visibility/topology, creation provenance, branch SHA and expected role. Primary naming uses `repo-rebuild-e2e-<8–32 lowercase alphanumeric>` for the existing minimal harness. Use distinct names for additional fixtures. Private repositories under the authenticated personal account, freshly created by operator, no archived repos, no preexisting content. If using organization/fork features not available in private personal fixtures, require separately approved sandbox org or disposable parent/fork; never use production parent. Do not enable Actions until workflow source is audited (only inert synthetic workloads, pinned actions, no deployment, no real third-party integration, no recursive dispatch; repo-scoped least-privilege tokens). Track quotas and artifact retention. Do not fabricate provider IDs or authorization.
4. Review a manifest of seeded paths, refs and objects, metadata and planned nonportable items before mutation. Store local immutable fixture plan/digest and creation receipts outside worktree. Distinguish setup authorization (create/populate) from DELETE approval (exact fixture name, numeric original ID, source and verified backups). For test-harness implementation itself, build source-bound native overlay, use native transaction and fresh hosted acceptance. Do not commit fixture credentials or user-specific data into Devtool.

## Gate B — minimal smoke, keep restrictive harness unchanged
Existing `tests/native_recovery_e2e_disposable.py` guards: personal owner == authenticated actor, fresh (<48h), private standalone, exact name/ack, admin, 1–8 refs, no existing issues/PRs, repo/Dependabot secrets or rulesets; exact clean source; independent filesystem; explicit policy; no archive-gap, local-only, missing-secret or blanket manual waiver. It is opt-in and excluded from ordinary discovery/CI. Its `--verify-session` requires original exact ack/name/source; no new backup/credential policy/waiver choice; explicit `--ack-app-repair` or `--ack-pat-provision` only for fixture writes. Use it on a separate minimal lifecycle fixture (or a deliberately planned initial minimal phase); do not populate rich metadata before this case or modify its restrictions. It cannot validate the complete matrix and `hosted_workload_qualified` is deliberately false.

A clean run must bind `disposable-live-acceptance.json` to source SHA, original/replacement IDs, exact original refs, independent backup, credential-predelete receipt and current admin. Credential-free run cannot verify PAT/App. Record session path as soon as created. Do not rerun destructive entrypoint after any deletion intent. If interrupted in an unsupported stage, inspect native session/report and exact live identity, continue only via verified recovery path; no manual state edits. A separate reviewed coordinator should make setup, prepare, delete, restore, resume, and verify checkpoints explicit rather than blindly rerun the monolithic harness.

## Gate C — rich fixture provisioning (new guarded harness required)
Build a separate full-feature harness (not implemented in this handoff) that admits only campaign-created resources and exact, planned inventories, rather than weakening `checked_disposable`. Independently verify IDs, source, owner, age, private/explicit scoped topology, metadata limits, allowlisted synthetic workflow contents and known credential policy before invoking the *actual native engine*, not an alternate recovery implementation. Refuse unexpected content, unknown inbound callers, active Actions runs, changed inventory, changed permissions, stale approval, dirty runtime or fixture drift. Keep a nonsecret plan and durable state separating user authorization, observed mutation intent and confirmation. Never retry non-idempotent POST/DELETE blindly. Use fixture token/keys only, disposable app installation scope only; no existing real secrets. Review actual API availability in plan; do not emulate unsupported behavior and call it live.

Seed deterministic payloads (small sizes and known hashes) on main, feature and a slash-named branch, annotated/lightweight tags as supported, Git LFS object, optionally a disposable gitlink/immutable pinned dependency. Create open/closed issue(s), comments, labels including meaningful metadata, milestones, open PR, closed unmerged PR and a merged PR with synthetic commits/reviews/comments/events; preserve base/head refs required for import. Use only fixture changes for that synthetic merge, with distinct approval; never merge Devtool or production. Add release/tag and small binary + valid ZIP asset; real completed workflow runs with success/failure and uploaded bounded artifacts/logs; disabled/default and branch-only workflow source cases. Add standard repo display settings, workflow token policy, allowlist/selected actions policy where supported, repository variables, environment variables and safe canary secrets, environment branch policy and protection options supported by account, deploy public key with separate private custody, repo ruleset/classic branch protection where allowed. For webhook, use owned inert endpoint or do not configure if none; archive sanitized metadata/manual obligation, not private token. Org-bound and Codespaces/Dependabot support may differ; document exact provider result. No live deployment. For secrets, use synthetic canary values in an independently encrypted age vault, with secure in-memory/stdin paths and non-secret success/failure assertions; no hash of low-entropy secret returned. Verify that original secret metadata alone cannot prove value. Select PAT/App policies explicitly and maintain host/consumer IDs; intentionally test missing/unavailable token and incorrect selection before approved valid preparation. Capture fixture manifest with old numeric IDs, expected source SHAs and hashes, refs, objects, registration states/config and metadata relationships. Any new run/metadata drift invalidates snapshot; settle all Actions runs before prepare/delete.

## Gate D — preparation and negative safety checks

Investigate expected nonportable items and authorize only specifically documented manual obligation(s), not blanket waivers. For intentional archive-gap behavior use a *separate negative* fixture or prepare-only test; no deletion with incomplete evidence in primary campaign. Prove no remote mutation on invalid policy, mismatched name/ID, missing admin, incomplete backup, changed independent copy, symlink/tamper, metadata/ref/run drift, expired credentials, changed policy/readiness/secret host/identity. Use disposable fixture or isolated copy and controlled failure injection (not damage to sole actual backup); preserve original evidence. Refuse legacy prepared sessions lacking new anchors; completed historical sessions inspectable. For uncertain or concurrent API outcomes test mock/fault transport with production network disabled, and optionally controlled real response-loss simulation only if reviewed transport can guarantee one actual mutation. Never induce uncontrolled races. Re-prepare after any real fixture changes; never edit manifest/journal or try to bypass refusal.

## Gate E — independently authorized deletion and recreation
Only after explicit approval for the current exact target/old ID and clean source, seal backup and readiness anchors and perform native `recovery execute` with the exact source/session. Do not approve changing any unrelated repository. Last-moment credential/readiness, admin actor, metadata/ref drift and original ID checks; durable delete-intent before DELETE. Observe absence and new ID distinct from old with same exact slug, privacy and topology. GitHub DELETE-by-name is not atomic compare-and-swap: prevent concurrent administration and preserve this residual limitation. Capture native journal and verify replacement provenance. Resume based on recorded stage and independent observations, not repeated deletion. Exercise interrupted create/adoption, restore, policy writes, PR import, lost response cases with safe fault injection or disposable-only controlled stages; declare what was live vs simulated. Recheck backup pair and independent copy after each resume. For an accidentally unapproved target or mismatching identity, immediately stop, preserve evidence.
